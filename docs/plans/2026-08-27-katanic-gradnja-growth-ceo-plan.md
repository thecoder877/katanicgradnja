Nova arhitektura ne dodaje API rute za javni sadržaj. Postojeće dinamičke rute, content accessors, Supabase CMS i statički katalog se ponovo koriste, ali ne u istom runtime režimu. Jedino novo trajno DB polje je opciono `projects.work_items text[]`; postojeća polja `location` i `year` konačno se izlažu kroz admin formu, a kategorija `Krovovi` proširuje postojeći ograničeni skup. Media batch identitet ne dobija novu kolonu: kodiran je u postojećem `storage_path` kao `{projectId}/{batchId}/{fileId}.{ext}`.

### Data Flow With Shadow Paths

```text
Supabase konfigurisan?
  ├─ NE ─▶ statički katalog ─▶ javna stranica
  └─ DA ─▶ public SELECT
            ├─ projekti ─▶ mapiranje ─▶ čisti selektori ─▶ javna stranica
            ├─ [] ──────▶ validno prazno stanje ─────────▶ bez lažnog fallback-a
            └─ greška ──▶ strukturirani warning ─────────▶ projekti privremeno nedostupni

Admin textarea ─▶ trim po redovima ─▶ ukloni prazne ─▶ Zod granice
  ├─ validno ─▶ work_items text[] ─▶ Supabase ─▶ mapProject ─▶ lista radova
  └─ invalidno ───────────────────────────────────────────▶ jasna admin greška

Novi projekat ─▶ INSERT published=false ─▶ upload + cover ─▶ publish-ready provera
  ├─ title + category + location + image + valid cover + sadržaj validni ─▶ dozvoli published=true
  └─ bilo koji korak nije potvrđen ───────────────────────────────────────▶ sačuvaj popravljiv draft
```

Granice za `workItems`: najviše 12 stavki, najviše 160 znakova po stavci i najviše 2.000 znakova pre parsiranja. `location` je opciono do 120 znakova, a `year` je opciona celobrojna vrednost od 1900. do naredne kalendarske godine. Pre uključivanja stroge `featured=true → location` validacije radi se audit postojećih statičkih i Supabase projekata: unosi se samo potvrđena lokacija, a projekat sa nepoznatom lokacijom privremeno gubi `featured`. React ostaje jedini renderer teksta; ne koristi se `dangerouslySetInnerHTML`.

### Media Batch Identity and Reconciliation

```text
storage path: {projectId}/{batchId}/{fileId}.{ext}
DB lookup: project_images.storage_path LIKE '{projectId}/{batchId}/%'

COMPLETE        = svaki očekivani fileId ima i Storage objekat i odgovarajući DB red; tretiraj operaciju kao uspeh bez cleanup-a
ABSENT          = nijedan očekivani fileId nema ni Storage objekat ni DB red; čist neuspeh bez cleanup-a
PARTIAL         = postoji samo deo očekivanih objekata/redova; pokreni best-effort cleanup potvrđenih batch zapisa
MANUAL_RECOVERY = PARTIAL cleanup nije potvrđen; critical log čuva projectId + batchId + korak
```

Ne uvodi se automatski reconciliation servis, tabela, cron ili background job. Runbook koristi identifikator samo kada stvarna operacija završi u `MANUAL_RECOVERY` stanju.

### Gallery State Machine

```text
CLOSED
  └─ click thumbnail(i) ─▶ OPEN(i) + showModal + fokus u dialog

OPEN(i)
  ├─ ArrowRight ─▶ OPEN((i + 1) mod n)
  ├─ ArrowLeft  ─▶ OPEN((i - 1 + n) mod n)
  ├─ Escape / close button ─▶ CLOSED + fokus na prethodni okidač
  └─ n = 0 ─▶ prelaz nije moguć; galerija se ne renderuje

Nevažeće stanje active >= n sprečava se otvaranjem samo iz postojeće liste.
```

Skaliranje: pri 10x sadašnjeg kataloga i dalje je prihvatljiv jedan mali SELECT. Pri stotinama ili hiljadama projekata prvi problem postaju prenos kompletnog kataloga i generisanje statičkih parametara; tek tada se uvode ciljane query funkcije i paginacija.

Rollback: aplikacioni deo je Git/Vercel revert. `work_items` je aditivna kolona i može ostati neiskorišćena. Stari category constraint i RLS politike imaju zasebnu rollback migraciju, ali se bezbednosno pooštravanje ne vraća osim ako admin pristup nije moguće obnoviti.

### Error Flow

```text
operation
  ├─ validation error ─▶ no external mutation ─▶ specific admin message
  ├─ DB/Storage error before mutation ─▶ stop ─▶ sanitized log + retryable message
  ├─ error after partial batch ─▶ read back state by batch id ─▶ compensate confirmed writes
  │                                                        ├─ cleanup succeeds ─▶ original error
  │                                                        └─ cleanup fails ─▶ CRITICAL reconciliation log
  └─ configured CMS read error ─▶ warning ─▶ project unavailable state without exposing internals
```

Delete invariant:

```text
project delete: unpublish DB → delete managed Storage → delete DB rows/project
  DB failure after Storage success → project remains unpublished + MANUAL_RECOVERY log

single image: update cover if needed → delete public DB association → delete managed Storage
  Storage failure after unlink → public-but-unreferenced orphan + exact storage_path log; no broken CMS reference
```

## Security & Threat Model

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Any authenticated account can mutate all content | Medium | High | Require `app_metadata.role = admin` in app, table RLS and Storage policies |
| Empty `ADMIN_EMAILS` opens application admin | Medium | High | Fail closed; configured allowlist remains defense in depth |
| Direct object reference through project/image UUID | Low after fix | High | `requireAdmin`, admin RLS and image ownership predicate |
| Script/HTML in descriptions or work items | Low | Medium | Zod length limits and normal React text rendering; no raw HTML |
| Malicious or mislabeled upload | Medium | High | Existing count/size limits plus byte sniffing and allowlisted MIME types |
| Secret key exposed to browser | Low | High | Continue publishable key only; existing guard rejects service-role/secret key |
| Stale JWT after adding admin role | High during rollout | Medium | Sign out/in and verify claim before policy migration |

The migration updates both table and Storage policies. `TO authenticated` alone is not authorization; every mutation policy also requires the trusted admin claim. Public read remains limited to published project rows and their images.

| Gallery | One image | No previous/next controls |
| Gallery | Keyboard navigation | Arrow keys cycle; Escape closes |
| Gallery | Focus/background | Native dialog traps focus; close returns focus to originating thumbnail |

| Mobile project rail | Horizontal gesture conflicts with page scroll | Test 360/390/430 px; fall back to grid if vertical scrolling is impaired |

## Code Quality Review

- Keep one `Project` type and one Supabase mapper; no page-specific project model.
- Wrap the non-`fetch` Supabase loader with React `cache()` as documented by the local Next 16 guide, then pass its result to pure selectors such as `selectFeaturedProjects` and `selectRelatedProjects`. Acceptance criterion: no repeated loader execution inside the same supported React render pass; verify the call count for page plus `generateMetadata`, without promising cross-request caching.
- Keep service content in `data/services.ts`; moving all services into Supabase is not justified.
- Add `Krovovi` through the existing category list, filter and constraint; do not introduce tags.
- Keep Motion absent unless the native dialog exit demonstrably needs interruptible unmount animation.
- Name cleanup failures separately from the original upload failure; never use an empty catch.
- Media invariants: every newly uploaded managed image row has a usable batch-prefixed `storage_path`; legacy/local/external rows may keep `storage_path = null`; a project with images has either a valid explicit cover or mapper fallback to its first image; managed destructive DB deletion follows confirmed Storage deletion; ambiguous outcomes are read back before compensation.

## Performance Review

- One memoized project-catalog read per request, shared by metadata/page consumers where the framework request boundary permits, then pure in-memory selectors.
- No new database indexes are needed for one `text[]` field that is displayed but never filtered.
- Keep the existing `projects_published_sort_idx` and `project_images_project_id_sort_idx` indexes.
- Use `next/image`, responsive `sizes`, optimized source assets and lazy loading below the fold.
- Only the measured LCP candidate receives `priority`; target mobile LCP ≤ 2.5 s and CLS ≤ 0.1 using the median of three production-like runs.
- Revisit targeted queries and pagination only when the catalog size or measured payload justifies them.

## Observability & Runbook

- Vercel Web Analytics: anonymous pageviews, routes and referrers only.
- Business ledger, weekly: source, service type, qualified call, visit agreed, quote delivered and job won; optionally record broad quote, material/labour, crew-day or gross-margin bands and a capacity/decline reason. Store no names, phone numbers or unnecessary personal data.
- The 60-day decision metric is won gross-profit potential per constrained crew-day where a rough band is available; otherwise use won jobs and capacity/decline reasons. Raw call count is a diagnostic, not the success criterion.
- Structured warnings: configured Supabase unavailable state, failed admin mutation, compensation failure, and cleanup failure.
- Logs include operation, project/image id when available, Supabase error code and cleanup status; never include auth tokens, full form content or file bytes.
- Runbook: CMS unavailable warning → check Supabase status/query/RLS without serving static mirrors; admin denial → verify fresh admin claim and allowlist; cleanup failure → search Vercel function logs by `projectId`/`batchId` within the configured retention window, list Storage objects under the exact batch prefix, query matching `project_images.storage_path`, then delete only the confirmed unmatched side and record the outcome. If log retention is shorter than the operating interval, copy the critical batch line into the release/incident record the same day.
- Delete runbook: a failed project delete is safe because `published=false` is confirmed first; reconcile stale hidden DB rows by project id. A failed single-image Storage cleanup is an orphan, not a broken public reference; use the logged exact `storage_path` for one manual remove attempt and record the result.

```text
1. Verify backups, `ADMIN_EMAILS` in preview/production, existing featured-project locations and the intended admin user
2. Set app_metadata.role = admin in Supabase Dashboard
3. Sign out/in and verify both the fresh JWT claim and allowlisted email
4. Create migration with Supabase CLI
5. Add work_items, Krovovi constraint and admin-only RLS/Storage policies; prepare `supabase/rollback/20260827_katanic_growth.sql`
6. Run advisors, anon/user/admin SQL/API probes and a rollback-policy rehearsal in preview/staging
7. Audit the configured remote CMS before authority switch: at least three published projects, valid cover/image references for every featured item, confirmed locations, and either a verified roof project or the approved general roof-service copy without fake proof
8. Deploy application to preview
9. Run lint + typecheck + focused unit + build; separately run focused Playwright public smoke, Supabase RLS probes and the measured Lighthouse check
10. Promote preview to production only after the content audit passes
11. First 5 min: routes, tel links, gallery, metadata, admin read
12. First hour: create a draft, complete it, publish/unpublish it and inspect logs/analytics
```

### Rollback Flow

```text
production issue?
  ├─ UI/code only ─▶ Vercel redeploy previous healthy build
  ├─ admin claim missing ─▶ restore claim + force fresh login; keep strict RLS
  ├─ RLS blocks valid admin after verified claim ─▶ apply prepared policy rollback
  └─ work_items/category issue ─▶ old code ignores additive field; fix forward preferred
```

No feature flag is needed: routes already exist, schema changes are additive except the explicit category constraint replacement, and Vercel rollback is fast. Migration runs before application code; old code safely ignores the new column and category until deploy. The tested rollback SQL is an emergency artifact, not an automatically applied down migration.

## Long-Term Trajectory

- Reversibility: 4/5. UI, selectors, metadata and analytics are easy to revert; the additive column can remain unused.
- Phase 2: collect at least one verified roof project, replace placeholders, update Google Business Profile and review qualified-call data after 60 days.
- Phase 3 is conditional: only expand local service pages, before/after media or targeted project queries when evidence justifies them.
- The content model stays understandable to a new engineer: services are curated code content, projects are CMS content, and a configured CMS failure never revives a static mirror.
